Thanks. The settled core is:

- `PUT /api/support/cases/{caseId}/assignee`
- Requires `accounts:write`.
- Tenant admins may reassign any case in their tenant.
- A support user may reassign only a case currently assigned to them; other support users receive `404`.
- The target must be assigned to that case’s account in `support_assignments`; otherwise `400`, atomically.
- `assigneeUserId` is required and cannot clear the assignment.
- Reassignment is allowed for any case status.
- Cross-tenant/invisible cases are `404`.
- Return exactly the seven requested fields.

❓ **Q8 — Same-assignee requests:** Should assigning the case to its current assignee be accepted as a successful no-op (`200`), or rejected as invalid (`400`)?

➡️ Recommended: accept it as idempotent success. This is friendly to retries and does not alter the security model.

---

❓ **Q9 — Support handover when unassigned:** If a case currently has no assignee, should a support user who is assigned to the case’s account be allowed to claim/reassign it, or must only the current case assignee perform the operation?

➡️ Recommended: only the current case assignee; an unassigned case is therefore admin-only through this endpoint. This follows your explicit “support user who currently has the case” rule.

---

❓ **Q10 — Admin role combinations:** If a caller has both `ADMIN` and `SUPPORT`, should the admin permission take precedence and allow any same-tenant case?

➡️ Recommended: yes; `ADMIN` is sufficient when the tenant matches.

---

❓ **Q11 — Successful HTTP status:** Should a successful reassignment return `200 OK` with the representation in the body?

➡️ Recommended: yes. `PUT` with a returned resource representation conventionally uses `200`.

---

❓ **Q12 — Unknown JSON fields:** Should the request accept and ignore extra fields, following the application’s existing Jackson behavior, or reject them?

➡️ Recommended: preserve existing behavior and ignore unknown fields; only validate the required `assigneeUserId`.
