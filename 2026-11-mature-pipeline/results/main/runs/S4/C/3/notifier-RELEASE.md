# Notifier rollout

Deploy notifier instances one at a time; no dependency on customer deployment order is required. Both customer versions publish the existing `offer.queued {customerId, offerId}` event, and both expose `consent.check`.

The new notifier creates only additive `capped` and `offer_day_lock` tables. Before processing an event it calls `customer.consent.check` for marketing and sends only explicit consent; an old customer therefore cannot cause a send after a failed customer rollout. A new customer emits only explicitly eligible events, so it also works with an old notifier. For eligible events, new instances count each customer's sent and capped offers within `floor(tick / 100)` while holding a per-customer/day database lock, then write either to `sent` or `capped`. Old `sent` rows remain visible and are included in the new instance's daily count. While old and new notifier instances coexist, an old instance can still add a `sent` row without applying the cap; the cap is fully enforced after the last old instance is replaced. The `sent` response retains `count` and `ticks` and adds `capped`, so callers that ignore extra fields remain compatible.

If rollout fails, stop and roll back to the previous notifier image. Do not remove either additive table; old instances ignore them and new instances can resume using the retained history. While an old notifier is running, a new customer still emits only explicit-consent events. If a customer rollout is rolled back while a new notifier remains, implied-consent events are rejected at processing time. Existing sent and capped rows remain safe to read; roll forward again when the cap is required on every instance.
