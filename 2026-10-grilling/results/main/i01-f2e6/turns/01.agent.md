I’m using the `grill-with-docs` skill first to pressure-test the endpoint design and capture any required domain/API decisions before implementing it.

I’ve checked the repository conventions and fixtures. The case model already has a nullable assignee, but there is no local user directory—identity is supplied by JWT claims—so the key design choices are authorization and how strictly to validate the replacement user.

❓ **Q1 — Who may reassign?**: Should this endpoint allow tenant `SUPPORT` users, tenant `ADMIN` users, or only admins? “Back office; customers can’t” permits either staff role, while the `/api/support/...` route suggests support staff are intended.

➡️ Recommended: allow `SUPPORT` and `ADMIN`, each restricted to their own tenant.

---

❓ **Q2 — Which cases may a support user target?**: Should a support caller be able to reassign only cases currently assigned to them (matching the existing support inbox visibility), or any case in their tenant? Admins would see all cases in their tenant either way.

➡️ Recommended: support users may change cases currently assigned to them; admins may change any case in their tenant. This prevents a support user from discovering or taking over another colleague’s queue.

---

❓ **Q3 — What makes an assignee valid?**: There is no users table or identity-service client in this codebase. Should `assigneeUserId` merely be a non-blank opaque identity ID, or must it be proven to be a support user in the same tenant through some existing local relation (which would exclude support users with no account assignment)?

➡️ Recommended: require a non-blank ID and treat it as an identity-service ID; enforce tenant boundaries on the case/caller, but do not incorrectly use account assignments as a proxy for staff membership.

---

❓ **Q4 — Case states**: Should reassignment work for every existing case status, or only `OPEN` cases? (The current fixtures only show `OPEN`, and there is no case-state transition policy in the API.)

➡️ Recommended: allow reassignment for any case status; this operation changes ownership, not lifecycle state.

---

❓ **Q5 — Documentation artefacts**: These choices are operational API policy rather than a hard-to-reverse architectural trade-off. Is it acceptable to record the resolved vocabulary in a root `GLOSSARY.md` and skip an ADR unless a deeper invariant emerges?

➡️ Recommended: yes—update the glossary only, and add an ADR only if we decide on a durable cross-service identity-validation rule.
