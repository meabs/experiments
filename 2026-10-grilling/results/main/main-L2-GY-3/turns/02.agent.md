The repository has no staff-user table or identity-service client—support identities exist only in JWT claims, while `support_assignments` tracks account coverage. Also, all fixture cases are currently `OPEN`; there is no case-status enum or mutator yet. That makes a few implementation-contract choices important:

❓ **Q6 — How can the target support user be validated?** Since this service cannot look up users or their roles, should it accept any nonblank `assigneeUserId` in the caller’s tenant context, or only ids appearing in `support_assignments`?

➡️ Recommendation: accept a nonblank id; tenant/role membership is an identity-service concern unavailable to this service. Do not incorrectly require account-assignment rows, because a valid support user may be on leave or newly onboarded.

---

❓ **Q7 — Support-user visibility versus reassignment:** A support user can currently list only cases assigned to themselves. Should the reassignment endpoint follow that same visibility rule (so they can reassign only their own cases), while admins can reassign any tenant case?

➡️ Recommendation: yes. This means an unassigned case can be reassigned by an admin, not by an ordinary support user.

---

❓ **Q8 — Status enforcement:** Given the current model only uses `"OPEN"`, should the endpoint explicitly require `status == "OPEN"` now, returning `409` otherwise, to preserve the agreed active-only rule?

➡️ Recommendation: yes; enforce `OPEN` and leave room for future terminal statuses.

---

❓ **Q9 — Path-specific authorization:** Should `/api/support/cases/...` be restricted to support/admin roles even if the caller has `accounts:write` (rather than relying only on method-level resource checks)?

➡️ Recommendation: require `SUPPORT` or `ADMIN` plus `accounts:write`; customers and approvers receive `403`.

❓ **Q6 — Target-user validation:** Since this service has no staff-user table or identity-service client, should it accept any nonblank `assigneeUserId`, or only ids appearing in `support_assignments`?

➡️ Recommendation: accept any nonblank id; user existence/role belongs to the identity service.

---

❓ **Q7 — Support visibility:** Should support users be able to reassign only cases currently assigned to themselves, while admins can reassign any case in their tenant?

➡️ Recommendation: yes.

---

❓ **Q8 — Status enforcement:** Should reassignment explicitly require `status == "OPEN"` and return `409` otherwise?

➡️ Recommendation: yes.

---

❓ **Q9 — Role restriction:** Should the endpoint require `SUPPORT` or `ADMIN` in addition to `accounts:write`?

➡️ Recommendation: yes; customers and approvers receive `403`.
