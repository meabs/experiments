- [k1] Call svc.apply(app) with the application dict; it returns a dict. Application fields are id, age, income, employment (employed or self_employed), requested_limit. (source: spec)
- [k3] handle(app, svc) returns {action, limit}; approve -> issue with returned limit, decline -> decline with limit 0, refer -> queue_review with limit 0 (do not decline). (source: spec)
- [k4] Network referral rule (all partners): a self_employed applicant whose requested_limit is above 6000 must be queue_review instead of issued, regardless of partner decision; a decline stays a decline. Threshold is strictly > 6000 (6000 is not referred). (source: spec)
- [k5] Verified via svc_call: a self_employed applicant with requested_limit 8000 (>6000) returns decision "approve" with limit 8000 — the handler must override this to queue_review. A self_employed applicant at exactly 6000 is NOT over the threshold (rule is strictly >6000). (source: svc_call t3 (self_employed, requested_limit 8000))
- [k6] Brightmoor is now on API v2: svc.apply returns {"api_version": 2, "result": {"outcome": "approved"|"declined"|"manual_review", "credit_limit": <int>}}. The v1 fields `decision` and `limit` are removed. (source: changelog)
- [k7] API v2 outcome mapping: "approved" -> issue, "declined" -> decline, "manual_review" -> queue_review (manual_review replaces v1 "refer" and is handled per spec section 3: do not decline). (source: changelog)
- [k8] Ticket KF-14 (Brightmoor): ops-lead suggested converting manual_review to decline to reduce wait complaints, but the spec (section 3) and changelog are explicit that manual_review must be queue_review, NOT decline. The handler keeps queue_review for manual_review. (source: ticket KF-14 / spec section 3 / changelog)
