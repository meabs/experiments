# Multi-agent swarms or a boring state machine?

**Status: design.** Written 2026-11-01, after two small pilots and before the measured run. Later changes go in the
amendment log at the end.

## Question

"Multi-agent swarms are the future" is a common claim. The alternative is unglamorous: a typed schema that a model
fills in, and plain `if`/`else` code that does the rest. When does a 3-agent crew with handoffs beat that state
machine, or a single agent, and what does it cost?

This is a sequel to [2026-10-need-an-agent](../2026-10-need-an-agent/) and uses its simulated shop, policy, tools,
cases and grader unchanged (imported, not copied: [`src/base.py`](src/base.py)). Like that experiment it includes
requests where the elaborate option should win: new level-6 emails that each contain two or three requests spanning
both specialists' areas, where splitting the work between specialists is the crew's selling point.

## What I expect (written before the main run)

- The state machine matches the single agent and the crew on levels 1 to 3 and costs least.
- Neither the state machine nor the crew recovers from tool faults (level 4) as well as the single agent.
- The crew's advantage, if it has one, is on level 6.
- The pilots already point the other way on level 6 (below). The hypotheses were not changed after the pilots; the
  pilot numbers are reported so readers can judge that.

## The shop and the cases

The shop (Hartley & Finch, a simulated UK homeware shop), policy, nine tools, faults and grader are need-an-agent's;
see its README. The 38 cases ([`src/crewcases.py`](src/crewcases.py)):

| Level | Cases | What it tests |
| --- | --- | --- |
| 1 simple | 6 | One lookup, or a policy question |
| 2 multi-step | 6 | A clear refund or replacement, everything stated |
| 3 branching | 8 | The outcome depends on what the lookups return |
| 4 recovery | 6 | A tool fails or the input is slightly off |
| 5 other requests | 6 | Address change, cancellation, two requests, double charge, "hold my order", two damaged items |
| **6 compound (new)** | 6 | Two or three requests in one email, across deliveries/order changes and returns/refunds/billing, with a policy question in three of them |

Level 6, written before any run here: L6-01 address change + damaged item (replacement) + "do you take Amex?"; L6-02
cancellation + return + "how long do refunds take?"; L6-03 where is it + a return outside 30 days (decline) + damaged
item (refund); L6-04 a £240 rug return (escalate to a manager) + damaged vase (replace) + "do you deliver to
Ireland?"; L6-05 parcel stuck two weeks (refund, as asked) + delivered but not received (escalate) + "PayPal?";
L6-06 a damaged clearance item that is out of stock (refund) + a return + a double charge (escalate to billing).
[`src/validate.py`](src/validate.py) checks them as need-an-agent's validator does (expected actions run, a reference
reply scores resolved, doing nothing or leaving out any one action isn't right, a doubled action is harmful, an empty
reply fails), and passes.

Every case runs in two wordings, the original and a paraphrase by a model not under test
(google/gemini-3.1-flash-lite, need-an-agent's prompt; [`cases/paraphrased.json`](cases/paraphrased.json); the 32 old
ones copied, the 6 new ones generated by [`src/paraphrase.py`](src/paraphrase.py)). I read the six new paraphrases:
all keep the order numbers, items, requests and preferences. L6-03's "Where is A1051?" became "check in on order
A1051 as I have not received it yet", which still asks where it is; not corrected. Each case runs with small and
large accounts (40 older orders added per customer), as in need-an-agent.

## The four architectures

All use the same shop, policy text and model per run.

| Architecture | File | What it is | Model calls per email |
| --- | --- | --- | --- |
| **State machine** | [`statemachine.py`](src/statemachine.py) | One call fills a typed schema: a list of requests, each with one of 9 intents (every kind of request the policy describes, plus "other") and its fields. Plain code handles each request with the policy as `if`/`else` (need-an-agent's helpers: reads retried twice on 5xx, writes never retried, a failed write escalated, an unknown order number searched by item). One call writes the reply from the facts. "Other" is escalated | 2 |
| **Single agent** | need-an-agent's [`agent.py`](../2026-10-need-an-agent/src/agent.py) | The model in a loop with all nine tools and the whole policy | as many as it needs, up to 20 |
| **Crew, shared history** | [`crew.py`](src/crew.py) | Three agents with handoffs: a **front desk** (looks up the customer and orders, answers policy questions, transfers; can't change anything), a **delivery** specialist (tracking, address changes, cancellations, escalation) and a **returns** specialist (refunds, replacements, stock, billing, escalation). Each has its own instructions, only its policy sections and only its tools, plus `transfer_to_<agent>(note)`. On a transfer the new agent sees the whole conversation so far (OpenAI Swarm's and the Agents SDK's default). The run ends when the active agent answers without a tool call | up to 20 in total |
| **Crew, note only** | [`crew.py`](src/crew.py) | The same crew, but on a transfer the new agent sees only the email and the transferring agent's note (a CrewAI-style task hand-off) | up to 20 in total |

The crew's instructions start with the OpenAI Agents SDK's recommended handoff prompt, verbatim, and a transfer's tool
result is `{"assistant": <agent>}`, as in the SDK. The single agent's step limit was raised from need-an-agent's 15 to
20 to match the crew's total budget. At the limit both escalate and send a holding reply.

**Models** (OpenRouter, billed price recorded per call), as in need-an-agent: `openai/gpt-6-luna` ($0.10 / $0.50 per
million input / output tokens) and `qwen/qwen3.7-flash` ($0.03 / $0.13). Default settings. Luna is the primary
model; Qwen is a replication.

## Measures

Per run, from the shop's record of state changes and the reply:

- **Outcome** ([`src/run.py`](src/run.py), need-an-agent's grader): **resolved** (exactly the right state changes and
  every required fact in the reply), **harmful** (a refund, replacement, cancellation or address change the policy
  didn't call for), **escalated** (handed to a person when not required, nothing harmful), **wrong** (anything else).
  One change for compound emails: several escalations in one run count as one, so escalating two requests separately
  isn't penalised.
- **False action claims:** the reply tells the customer something was done (a refund, replacement, cancellation,
  address change, or handing it to a team) that the shop's log shows wasn't. Labelled by a judge model
  (openai/gpt-6-luna, JSON mode), which lists the actions the reply says were taken; these are compared with the log in
  code. I check by hand every positive and a random 10% of negatives, and report agreement.
- **Handoffs** per run (crew), and whether the front desk replied without handing over when an action was needed.
- **Cost** (OpenRouter's billed cost), **model calls**, **tokens**, **wall time**, **consistency** (share of case ×
  wording × account conditions where all five repetitions ended the same way).

## Hypotheses

For each model separately (Luna primary, Qwen replication), outcome = resolved:

- **H1 (where code should win):** on levels 1 to 3, the state machine resolves more than the shared-history crew.
- **H2 (where the crew should win):** on level 6, the shared-history crew resolves more than the single agent.
- **H3 (handoff style):** over all levels, the shared-history and note-only crews differ (two-sided: before the
  pilots I expected shared to be better; the pilots showed the opposite).

Tests: permutation tests with arm labels shuffled within case × wording × account size (10,000, seed 1); one-sided for
H1 and H2, two-sided for H3; Holm over H1 to H3 within each model. Rates have Wilson 95% intervals. A
non-significant result is reported as "no measurable difference". Everything else (levels 4 and 5, false action
claims, cost, harm, consistency) is descriptive.

## Size

38 cases × 2 wordings × 2 account sizes × 5 repetitions = 760 runs per architecture and model; 4 architectures × 2
models = **6,080 runs**, shuffled (seed 1), 16 in parallel. Expected cost from the pilots: about $2.50 for the runs
and about $1 for the judge.

| Single agent, Luna | 6/6 | 6/6 | 8/8 | 4/6 | 6/6 | 6/6 | $0.009 |

| Crew note, Luna (pilot 2) | 6/6 | 6/6 | 8/8 | 5/6 | 5/6 | 6/6 | $0.018 |
| State machine, Qwen | 6/6 | 6/6 | 6/8 | 4/6 | 6/6 | 5/6 | $0.016 |
| Single agent, Qwen | 6/6 | 6/6 | 7/8 | 4/6 | 6/6 | 4/6 | $0.008 |
| Crew shared, Qwen (pilot 2) | 6/6 | 4/6 | 7/8 | 2/6 | 4/6 | 1/6 | $0.017 |
| Crew note, Qwen (pilot 2) | 6/6 | 5/6 | 7/8 | 3/6 | 6/6 | 2/6 | $0.017 |

- **Pilot 1** (304 runs, $0.11): no crashes. In the shared-history crew, receiving specialists often wrote "I've
  passed your request to our delivery team" instead of doing the work. My transfer result ("transferred to delivery")
  and instructions were less explicit than the frameworks', so the crew now uses the Agents SDK's handoff prompt and
  tool result (above).
- **Pilot 2** (152 runs, crews only, $0.07): a small improvement for the shared crew with Luna; still behind. The
  front desk often answered without handing over and told the customer the refund or escalation was done although it
  has no tool that can do either. That is why false action claims are measured.
- **Ceiling:** the state machine and the single agent with Luna are at or near the ceiling outside level 4, so H2
  is unlikely to be supported. It stays, because "the crew wins on compound requests" is the claim under test.

## Threats to validity

- **I wrote the shop, the cases, the state machine and the crew.** The state machine's schema covers every request
  type in the policy, and I knew the cases while writing it; the paraphrased wording counters this only for the
  language side. A real state machine meets requests its schema doesn't have; here those are escalated.
- **One crew design.** Other splits (by order, or a manager calling specialists as tools), other prompts or a stronger
  model could do better. The handoff prompt is the Agents SDK's; the roles are mine.
- **One small domain** that naturally suits a state machine.
- **Two cheap models at default settings.**
- **The judge** for false action claims is one of the models under test; it is checked by hand as described.

## Reproducing

```bash
python3 -I src/validate.py                        # the level-6 cases and the grading change, no model
python3 -I src/paraphrase.py                      # level-6 paraphrases (already committed)
python3 -I src/run.py <out> --reps 5              # 6,080 runs; needs ~/.config/openrouter.key
python3 -I src/judge.py <out>                     # false action claims
python3 -I src/analyse.py <out> > results/analysis.md
```
