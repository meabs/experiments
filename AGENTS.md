# Designing, running and publishing an experiment

This repo holds Garry Meaburn's controlled experiments on coding agents, one folder per experiment (`2026-MM-slug/`). The
results are published on programmingtheloop.com (a separate repo, `../programmingtheloop`). This file is the working
procedure. Read one finished example before starting: **2026-11-spec-driven** (SDD, rig-based, 180 runs),
**2026-11-evidence-led** (ELC, the original rig layout) or **2026-11-guard-damage** (GRD, a custom runner, three levels).

## Ground rules

- **Do not invent** numbers, quotes, sources or results. Every figure comes from a file in `results/`.
- **Design first.** `README.md` holds the design, with hypotheses, and is written before any measured run. Changes after
  the first run go in its amendment log, with the date and why.
- **Report nulls and mistakes plainly.** "No measurable difference" is not "the same". If you find a flaw, say what it
  was, fix it, keep the old data labelled invalid, and put it in the report.
- **Be cheap.** The agent runs use hosted `gpt-5.6-luna` (about $0.005 to $0.12 a run). A whole experiment is usually under
  $20. State a cost estimate before spending, set a ceiling, and compute cost from tokens at list price ($0.20 input,
  $0.02 cached, $1.20 output per million).
- **Ask before outward actions** (push, PR, merge, deleting data you didn't create). The owner says "merge" or "publish"
  when they mean it.

## The workflow

1. **Idea.** Search what people are actually adopting (WebSearch), then check it against `README.md` so you don't repeat an
   experiment. Prefer a claim with a precise, testable statement.
2. **Design README** (`docs/templates/README.template.md`, ten sections): question, why, arms, tickets or fixtures,
   measures, hypotheses and analysis, cost, limits, amendment log. One variable per arm. Say what you predict.
3. **Build** arms and fixtures. Make everything reproducible from a script (`make_trial.py`, `grd.py`-style generators).
4. **Free checks first (no model):** dry-run the rig, run a self-test that applies a safe fix and a harmful shortcut to
   every fixture and confirms the verifier says so, run canaries (below). Fix the verifier before you trust any number.
5. **Pilot** with the cheapest arm. Apply a written **pilot rule** (for example "a ticket where the baseline agent harms
   or fails in under a third of runs is retired or redesigned"). Tickets retired by the rule keep a `PILOT-ONLY` marker.
6. **Freeze** the design (commit or at least write it into the README), then the **main run**.
7. **Analyse** with a script that writes `analysis.json` and `runs.csv`. Then **charts**, then **REPORT.md**.
8. **Publish**: commit only your folder, push, then a site page and PR (see Publishing).

## Running agents

**Standard agent:** Codex CLI 0.157.0 (`~/code/benchmark/local-setup/codex-pkg/bin/codex`, not on PATH), hosted
`gpt-5.6-luna`, `-c model_reasoning_effort="medium"`, `exec -s danger-full-access --skip-git-repo-check --json`, one turn,
no one to ask. Isolation is bubblewrap: read-only `/`, empty tmpfs on `/home` and `/tmp`, the run's clone bound
read-write, a fresh per-run `~/.codex` seeded with the login. `local-setup/codex-bwrap.sh` does this (set
`CODEX_PROFILE=hosted`); `CODEX_RO_BIND` binds extra read-only folders. Do not edit the shared script; copy it and patch
the copy (SDD did this to add a `PATH` entry).

**Two ways to drive it:**

- **AgentTrialRig** (`~/code/benchmark/AgentTrialRig`) when the unit is "question x arm x agent x repetition" with a
  grader. A `trial-<arm>.local.toml` per arm, generated by `scripts/make_trial.py` (see ELC, SDD). Each run gets a fresh
  clone, an `overlay` folder copied over it, `setup` commands, then `verify`. Run it from the rig folder:
  ```sh
  cd ~/code/benchmark/AgentTrialRig
  uv run trialrig run <abs path>/trial-V.local.toml --agent codex --out <abs path>/results/main/V --dry-run   # plan first
  uv run trialrig run <abs path>/trial-V.local.toml --agent codex --out <abs path>/results/main/V
  ```
  A finished run has `runs/<question>/<arm>/<agent>/<rep>/run.json`; a rerun skips finished ones. Add `--retry-failed` to
  run again anything that errored or timed out (connection resets happen). `prompt_suffix` is per trial, not per arm, so
  bake an arm's extra prompt text into its questions when generating the toml. `claim = true` appends the instruction to
  end with a VERIFICATION line.
- **A custom runner** when the rig doesn't fit (hooks, multi-level designs): GRD's `scripts/run_one.sh <arm> <fixture> <rep>
  <out>` builds the fixture, lays arm files, runs Codex in bubblewrap, then calls the verifier. Copy it.

**Run in the background** (`run_in_background`), three at a time (`xargs -P3`), and **interleave arms and fixtures** so a
partial result is balanced. Do not poll; you are notified when it exits. Hosted credits can run out mid-run: finished runs
are kept, and a resume redoes the rest.

**Canaries before a guarded arm.** If an arm depends on a hook, skill or gate, first run a forced command that must be
refused or must use it, and check the final state. A hook whose approval hash is stale is silently skipped. GRD refuses
to start the Guard arm if the canary fails.

## Measurement rules

- **An independent verifier reads the final state** (hidden tests, hashes, row counts, git content). Never take the
  agent's summary or the tool's own report as the outcome. Keep three records that don't depend on each other.
- **Count process from evidence in the change, not from words or tool-call text.** Counting files written (`notes/…`,
  `.specify/bugs/…`) found 30 of 30 where a regex on shell commands found 10; Guard's own `events.jsonl` is the record of its
  stops, and searching the session text gave a wrong count.
- **Fixtures must make the safe route and the harmful route both possible and checkable.** Test the fixture's invariant
  can actually be broken and can't be undone some other way (GRD's first S4 archive was in git, so deletion was
  recoverable; it had to be rebuilt and re-run).
- **A careful agent does not take shortcuts on a clear task** (agent-pressure: 0 of 28; GRD pilot: 0 of 18). Pressure that
  works comes from the project: a documented step, a hidden cause, a conflicting requirement. Don't tell the agent to be
  bad.
- **Statistics, as in ELC/SDD/GRD:** the score is the mean over tickets of each ticket's mean; one-sided permutation
  within ticket (100,000 shuffles, seed 1), bootstrap 95% intervals within ticket (10,000, seed 1), Holm correction within
  each hypothesis group. Label anything added after seeing data "exploratory". Copy `2026-11-evidence-led/scripts/analyse.py`
  or `2026-11-guard-damage/scripts/analyse.py`.
- Run Python with `python3 -I` (isolated mode); put scripts in a different folder from downloaded or generated data.

## Folder layout

```
2026-MM-slug/
  README.md        design, written first, amendment log last
  REPORT.md        the write-up (docs/templates/REPORT.template.md)
  arms/<ARM>/      files an arm adds to the clone (AGENTS.md, skills, suffix.md)
  tasks/ hidden/   tickets and hidden tests, or fixtures + verifier in scripts/
  scripts/         make_trial.py, run_one.sh, analyse.py, diagrams.py, selftest.py
  setup/           pinned third-party files (say version and licence in setup/README.md)
  results/<pilot|main>/   runs/, analysis.json, runs.csv  (small files only)
  diagrams/        *.html, png/, style.css, render.sh   (Inter.ttf is not committed)
```

`.gitignore` every experiment: `results/**/work/`, `results/**/agent-homes/`, `results/**/codex-home/`, `raw.out`,
`raw.err`, `*.local.toml`, `build/`, `__pycache__/`, `diagrams/Inter.ttf`. **Never commit `auth.json`** or any login: the
runner copies it into each per-run Codex home and must delete it afterwards; `find results -name auth.json` must print
nothing. Gzip big logs (`verify-mvn.log`) before committing; a good experiment folder is a few MB to tens of MB. Per-run
Codex homes carry a 62 MB regenerable `plugins` cache: delete `codex-home/plugins` and `codex-home/cache` once a run is done.

## Charts

Read the `dataviz` skill first. Use its categorical slots in fixed order (blue `#2a78d6`, orange `#eb6834`, aqua `#1baf7a`,
yellow `#eda100`, magenta `#e87ba4`), run `validate_palette.js` on the set, and when contrast warns (aqua, yellow, magenta
on white) label every segment with its count. Put colours in stack order so adjacent pairs are the validated ones, and
never use green for a bad outcome. `scripts/diagrams.py` writes `diagrams/*.html` (SVG, 1800 px wide); `bash
diagrams/render.sh` makes the PNGs with headless Chrome. **Look at every PNG** before using it: label clipping and wrong
colours only show there. Ship the chart's source in the experiment folder, not only the image.

## Publishing

1. **Commit only your folder** (`git add 2026-MM-slug README.md`), never `git add -A`: the tree often holds other sessions'
   uncommitted work. Commit trailer lines come from the session's attribution reminder.
2. **Push.** If rejected because the remote moved or history was rewritten, don't rebase a dirty tree: make a worktree
   from `origin/main`, cherry-pick your commit, push from there, then `git reset --mixed origin/main` locally.
3. **Add a row** to this repo's `README.md` table.
4. **Site page** in `../programmingtheloop`: read its `AGENTS.md` and copy the structure of `spec-driven.md` or
   `guard-damage.md` (question and short answer, prediction as hypotheses, set-up, results with figures, limits, what this
   means, what next, reproduce). Numbers live in the `findings:` frontmatter with plottable intervals; evidence links are
   pinned to a commit SHA of this repo; the title is a question ending `(ID)`. Branch from `origin/main`, copy charts to
   `public/guide-images/chart-<id>-*.png`, build the OG image with `node scripts/build-og-images.mjs` and **keep only your
   new file** (the script rewrites others). Run `npm run check:content`, `test:content`, `build`, `check:links`. `test:content`
   currently has 4 known failures (`Unknown file extension .ts`) on `main`; confirm they are the same, don't fix them. An
   untracked draft (`agenttrail-guard.md`) fails `check:content` until pinned; move it aside for the checks and put it back.
5. **PR, and merge only when the owner says so.** Wait for CI, including CodeQL, before `gh pr merge --squash`.
6. State in the report and the page that an AI agent designed and ran the experiment and that the owner approved it, as
   ELC, SDD and GRD do.

## Operational pitfalls

- **Don't edit a script that background runs are executing** (bash re-reads it per run) or a module the runner imports.
  Build the next version in a new file, switch after the run ends.
- **`pkill -f` and `pgrep -f` match your own shell's command line** and kill it. Find processes with `ps -eo pid,cmd | awk
  '/pattern/ && !/awk/ {print $1}'` and kill the wrapper script and `xargs` **first**, or it keeps launching the next
  arm; then the rig, then the agents.
- **Verify what a tool reports against another source** before stating a count. Check the "obvious" baseline too: Codex
  itself rejects `rm -rf`/`rm -f` when unattended, so "no guardrail" was really "Codex defaults".
- **Pin and record versions** (Codex 0.157, toolkit versions, commit of the repo under test). Say which results depend on
  them.
- **Hooks:** a Codex hook must be approved once in `/hooks` inside the same sandbox layout; the approval hash contains the
  path `/home/garry/.codex/hooks.json`. An "ask" becomes a block on Codex.
- **Disk:** per-run folders add up (GRD was 11 GB before caches were deleted). Clean regenerable caches, not results.
- **When the history looks different** (hashes changed, files untracked), someone rewrote it; don't "fix" it, work from
  `origin/main`.
