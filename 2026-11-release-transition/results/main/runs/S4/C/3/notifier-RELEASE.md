# Notifier rollout

Drain the event queue, then switch customer and notifier together, all instances at once, with no traffic between the old and new pair. Both customer versions publish the existing `offer.queued {customerId, offerId}` event, and the new notifier calls the additive `customer.consent.check` operation when consuming it. The atomic switch is required because an old notifier cannot re-check the new customer consent rule.

The new version creates the additive `offer_daily` table and backfills it from `sent`. While old and new notifier instances coexist, they share the existing `sent` table and the new daily state; the new version returns the additional `capped` field, while the old version ignores the new table and continues its old response shape. New notifier instances enforce two sends per customer per platform day and count later offers in `capped`. Before writing `sent`, a new instance re-checks current marketing consent, so queued events from before the customer rule change are not sent after opt-in becomes required. If an old customer instance does not expose the additive check, the notifier accepts the legacy event; other customer-call failures are retried.

To roll back, switch customer and notifier back together, again with no traffic between versions. Do not drop either table: old code continues to use `sent`, and retaining `offer_daily` preserves the new counters for a later forward deployment. If an unavailable consent endpoint is encountered, the new notifier accepts the legacy event for compatibility with the old customer version; other customer-call failures leave queued events for retry.
