# Accounts service FMEA

## Scope and scoring

This FMEA covers the Spring Boot accounts API, its H2/JPA persistence, bearer-token
security boundary, payment workflow, scheduled queued-payment job, and the scheme,
fraud, ledger and notification integrations. It is based on the implementation and
configuration in this repository, including the current `application.yml`. Scores
are on a 1–10 scale: severity (S) is impact if the failure occurs, occurrence (O)
is expected frequency without the recommended action, and detection (D) is how
unlikely the failure is to be detected promptly (10 = hardest to detect). The risk
priority number is `S × O × D`; higher numbers should be addressed first. These are
initial engineering estimates and should be recalibrated against production
telemetry and incident history.

| Failure mode | Likely cause | Effect on customers, dependent systems and teams | Detection / existing controls | S | O | D | RPN | Recommended action |
|---|---|---|---|---:|---:|---:|---:|---|
| **Persistent account, payment or case data is lost or replaced after restart** | `application.yml` uses `jdbc:h2:mem:accounts`, `ddl-auto: create-drop`, and always runs `data.sql`. There is no production database profile or migration strategy in the repository. | Customers can see stale fixture data or lose newly created cases, closure requests and payments. Balances and payment history can diverge from the ledger. Support, operations and reconciliation teams cannot trust the service after a deploy or crash. | Restart test against a persistent test dataset; compare database row counts and payment IDs before/after restart; database durability and startup smoke checks. Current application health does not validate persistence. | 10 | 6 | 9 | **540** | Block production release until a durable, tenant-safe database is configured. Use migrations (for example, Flyway/Liquibase), disable fixture loading outside tests, take backups, and run restore/restart tests. |
| **A payment is accepted by the scheme but the API reports failure or a retry creates a duplicate** | The scheme call is external to the database transaction. A timeout or later exception can roll back the local payment even if the scheme accepted it; the request has no explicit idempotency key or reconciliation path. | A customer may see an error and retry, causing duplicate outgoing payments, or see no durable record of an instruction that left the bank. The scheme, ledger, finance and customer-support teams must manually reconcile money movement. | Alert on scheme timeout/error rates and compare scheme instructions with local payments and ledger postings. Synthetic tests must force “accepted then timeout”; current code has no durable outbox/reconciliation metric. | 10 | 5 | 9 | **450** | Use a durable payment state machine and outbox. Send a stable payment ID as an idempotency key, persist “submitted/unknown” before/around the call, query or reconcile ambiguous scheme results, and make client retries idempotent. |
| **Scheme accepted but ledger posting remains inconsistent** | `PaymentDispatcher` debits the local account after scheme submission, then catches only `LedgerTimeoutException`. A ledger HTTP error can escape; a timeout leaves `POSTING_FAILED` with no retry job or operator action. | The external payment may complete while the account/ledger view is wrong. Customers see incorrect balances or a stuck payment; finance and ledger operations need urgent reconciliation. | Alert on `POSTING_FAILED`, compare scheme receipts, account debits and ledger postings by payment ID, and add a reconciliation dashboard. Current detection is only a warning log for timeouts. | 10 | 6 | 8 | **480** | Make ledger posting idempotent on `ledgerReference`, add durable retry with bounded backoff and a dead-letter/manual-repair queue, and expose reconciliation status. Treat unknown outcomes as explicitly recoverable rather than generic request failure. |
| **Queued payments are not executed on time or are executed twice** | The only dispatcher is an in-process `@Scheduled` job at 06:00 Europe/London. There is no durable job lock/claim, misfire recovery, retry policy, or evidence that scheduling is enabled in the deployment. Multiple instances can process the same row concurrently. | Customers miss payment cut-offs or incur late fees; duplicate scheme submissions are possible in a multi-instance deployment. Support and payments operations must handle missed/duplicate instructions. | Metric for due queue age, job duration, claimed/completed/failed counts, and alert when due rows remain after 06:00. Run a multi-instance/concurrent-job test and inspect scheme idempotency. | 9 | 6 | 8 | **432** | Move dispatch to a durable queue/worker or implement database row claiming with locking, leases and idempotent dispatch. Add misfire recovery, retry/dead-letter handling and a daily due-payment reconciliation. |
| **Fraud screening is bypassed or its outage is invisible** | A fraud client and timeout are configured, but no production code calls `FraudScreeningClient`; the payment path submits directly to the scheme. | Fraudulent payments can leave the bank without a screening decision. Fraud operations lose a control point and may not know screening is absent; customers and the bank bear financial and regulatory exposure. | Compare payment volume with fraud-screening decision volume; alert when the ratio is not 1:1. Add an integration contract test that requires screening before submission. Current tests use a fake, but the application path does not invoke it. | 10 | 5 | 10 | **500** | Put screening in the payment state machine before scheme submission, fail closed or explicitly queue for review on unavailable/indeterminate results, persist the decision and correlation ID, and alert on bypasses. |
| **A downstream outage or slow response exhausts request threads and causes broad API unavailability** | Scheme (10s), ledger (5s) and fraud (2s) have synchronous calls; notifications have no configured connect/read timeout. There is no circuit breaker, bulkhead, rate limit or dependency-specific concurrency limit. | Payment requests become slow or fail; account, case and support API traffic can be starved if the service pool fills. Customers receive timeouts and support teams see an outage cascade. | Track latency, timeout rate, HTTP status by dependency, in-flight requests, thread-pool saturation and queue depth. Use dependency health probes and timeout fault injection. Existing logging is WARN-only and notification calls can hang at the client default. | 9 | 6 | 7 | **378** | Set explicit notification timeouts, add connection pools/bulkheads, circuit breakers and bounded retries only for idempotent operations. Separate payment workers from read/API capacity and alert on saturation. |
| **Cross-tenant or over-privileged data/action is exposed** | Tenant and resource checks are distributed across services and repository queries; a future endpoint or query can omit a check. Admin access is based on token claims, and there is no database-level tenant guard or authorization audit trail. | A customer or staff member could view another bank’s accounts, transactions, customer PII, internal cases/notes or initiate an action. This creates a severe privacy, financial and regulatory incident for affected tenants and security/compliance teams. | Automated negative tests for every endpoint with same IDs across tenants; authorization decision logs without sensitive payloads; periodic access review and audit queries. Current tests cover key cases but do not provide runtime detection. | 10 | 3 | 9 | **270** | Centralize tenant/resource authorization, enforce tenant predicates at repository/database boundaries, add deny-by-default endpoint tests and security regression tests, and emit auditable subject/tenant/resource/action events. |
| **A token is accepted with incorrect authorities or stale/invalid identity data** | JWT claims are mapped from `roles` and `scope` without an issuer/audience configuration shown in `application.yml`; key rotation and identity-service failure handling are not documented. Claim shape or signing-key changes can silently alter access. | Legitimate users receive 401/403 and cannot access accounts, or an incorrectly trusted token gains customer/staff/admin capabilities. Identity, support and security teams face an incident or broad access outage. | Monitor 401/403 rate by issuer/client/endpoint, validate tokens with key-rotation and malformed-claim tests, and alert on unexpected role/scope distributions. | 10 | 3 | 8 | **240** | Configure and validate issuer, audience, key rotation and clock-skew policy; test claim compatibility; fail closed on invalid claims; monitor authorization failures and key-refresh errors. |
| **Payment limits and balances are bypassed under concurrent requests** | `PaymentService` reads balance and today’s payments, then saves/dispatches without an account lock or atomic reservation. Two requests can both pass the balance/daily-limit checks. | Customers can overspend or exceed bank limits; local balance, scheme payments and ledger postings diverge. Fraud, finance and support teams need remediation. | Concurrent load tests for one account; reconcile sum of accepted payments against balance and daily limit; alert on negative/limit-exceeding balances. Current unit/API tests are not a concurrency control. | 9 | 5 | 8 | **360** | Reserve funds and daily-limit capacity atomically in the durable ledger/database, use optimistic/pessimistic locking or a serialized account queue, and add a unique/idempotency key for client retries. |
| **Account closure is requested but never completed, or payments continue against a closing account** | The endpoint creates a pending request, but this repository has no approval/decision endpoint or transaction that changes `Account.status`; payment creation checks only `OPEN`. | Customers and approvers see requests that remain pending indefinitely; an account intended for closure can continue sending payments. Operations and compliance teams cannot demonstrate closure control. | Alert on pending-request age and mismatch between approved closure records and account status; end-to-end closure workflow test. Current API exposes pending requests but no completion path. | 8 | 6 | 8 | **384** | Implement an explicit approve/reject workflow with separation of duties, atomically transition account state, reject new payments once closure is approved/in progress, and reconcile closure state daily. |
| **Notification failure hides a completed payment from the customer** | Notification is best-effort and exceptions are caught/logged; there is no outbox, retry or delivery status. | Money may move while the customer receives no confirmation, increasing duplicate retries, complaints and support load. Notification operations cannot reliably prove delivery. | Compare completed/submitted payments with notification delivery receipts; alert on outbox age/failure rate. Current detection is a log warning only. | 7 | 7 | 8 | **392** | Publish a transactional notification outbox keyed by payment ID, retry with backoff and dead-letter failures, expose delivery status, and ensure the notification consumer is idempotent. |
| **Operational monitoring reports healthy while the service is unhealthy** | `SecurityConfig` permits `/actuator/health`, but `spring-boot-starter-actuator` is absent from `pom.xml`; there are no application metrics, readiness checks, dependency probes or structured audit logs. | Load balancers and on-call staff may not detect a dead or degraded instance. Incidents last longer and dependent teams receive late or misleading status. | Probe the actual health URL from deployment; startup test must assert expected status and dependency indicators. Add alerts for error/latency, queue age, DB connectivity and reconciliation gaps. | 9 | 7 | 9 | **567** | Add Actuator and expose only authenticated/controlled liveness/readiness endpoints as appropriate; implement DB and dependency readiness checks, Micrometer metrics, correlation IDs, structured logs and SLO alerts. |
| **Malformed or unexpected integration responses cause 5xx errors or corrupt state** | Clients assume response fields/types (`instructionId`, `decision`, `reasonCode`); HTTP error handling is incomplete (for example, ledger catches only connection access errors), and notification responses have no validation. | Payments may be stuck, rejected incorrectly, or become ambiguous. Customers see generic errors; integration owners and developers must investigate payload incompatibilities. | Contract tests against versioned schemas; alert on 5xx and parsing exceptions; retain sanitized request/response correlation data. | 8 | 4 | 7 | **224** | Define versioned schemas and validate responses, handle all expected status classes explicitly, map failures to durable states, and use contract/consumer-driven tests in release gates. |
| **Service startup or deployment fails, or a bad configuration reaches production** | Integration URLs/timeouts and JWT key are configuration-driven, with no shown validation for blank URLs, missing keys, unsafe profiles or incompatible schema. The in-memory database also makes startup destructive. | The API may be unavailable after release, or it may start against the wrong scheme/ledger/tenant data. Customers and all dependent teams are affected immediately. | Startup smoke test with production-like configuration; validate configuration at boot; deployment health gate and rollback alarm. | 9 | 4 | 6 | **216** | Add typed validation (`@Validated`/not-null/range checks), environment-specific profiles, secret/key and endpoint verification, migration checks, canary deployment and automated rollback. |

## Highest-priority release actions

Before release, the service should at minimum have durable production persistence
with migrations, a real health/readiness and metrics surface, fraud screening wired
into the payment state machine, and an idempotent/reconcilable payment workflow for
scheme and ledger ambiguity. The queued-payment worker and closure workflow also
need durable retry/ownership and completion semantics. These controls should be
validated with restart, dependency fault-injection, concurrent-payment,
multi-instance scheduler, cross-tenant authorization and reconciliation tests.

## Evidence and limits

The repository contains API tests with fake integrations and signed test tokens,
but it does not show production deployment manifests, database configuration,
observability configuration, runbooks, traffic volumes or incident history. The
occurrence and detection scores therefore reflect implementation-based risk, not a
measured production rate. The FMEA should be re-scored when those operational
artifacts and telemetry are available.
