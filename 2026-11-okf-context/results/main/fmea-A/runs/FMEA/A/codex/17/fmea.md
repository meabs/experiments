# Accounts service FMEA

Assessment date: 4 November 2026. Scope: the Spring Boot API, its H2/JPA persistence configuration, authentication and tenant authorization, payment workflow, scheduled dispatch, and the scheme, fraud, ledger and notification integrations. This is a release-readiness assessment of the repository as it stands; deployment-specific controls may reduce some scores.

## Scoring

Each score is from 1 (low) to 10 (high). Severity measures the consequence if the failure occurs, occurrence is the estimated likelihood without the recommended action, and detection measures how unlikely the existing controls are to detect it promptly (10 = difficult to detect). `RPN = severity × occurrence × detection`; higher RPNs should be addressed first. Detection entries describe the signals that should be used in production, as well as the control currently visible in the code.

| 6 | Payment is submitted twice to the scheme | Scheme request times out after acceptance, the caller retries, or two workers/processes dispatch the same queued payment. | 7 | Concurrent payments bypass balance or daily-limit checks | `PaymentService` reads balance and today’s payments without a lock or serializable transaction; simultaneous requests can both pass before either debit is committed. | Overspending, negative or incorrect local balance, and violation of bank-configured daily limits; downstream scheme and ledger may process funds the service should have rejected. | Alert on negative balance, daily-limit exceptions and account/ledger imbalance; concurrency/load tests should issue simultaneous payments. Current code has no retry isolation or job telemetry. | 8 | 5 | 7 | 280 | Move dispatch to a durable queue/work table with leases, retries and dead-letter handling; process each payment independently; make the job replay-safe and alert on overdue queued records. |

## Priority actions before release

1. Gate payment submission on a persisted fraud decision and implement idempotent, reconciled scheme/ledger processing. Address the concurrent balance/daily-limit race at the same time.
2. Add durable queued-payment processing with leases/retries and operational metrics; test scheme 5xx, timeout-after-acceptance, ledger timeout and worker restart scenarios.
3. Enforce `accounts:write` on every state-changing endpoint, then complete and secure the closure maker-checker workflow, including a database uniqueness constraint and auditable approval/rejection.
4. Establish tenant/privacy regression tests for every endpoint and production observability for payment state mismatches, overdue work and authorization anomalies.
5. Replace the default in-memory persistence configuration for production and verify backup/restore and key-rotation procedures.
