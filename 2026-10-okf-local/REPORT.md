# Is a code guide worth more to a small local model? Report

Run on 2026-10-28, from 00:05 to 06:33. The design is in [README.md](README.md), committed and pushed before any measured run; later changes are in its amendment log. Every run's grading log, the rig's record and its event stream from Codex are in [results/main](results/main). The raw Codex session files aren't published. The analysis is [results/analysis.md](results/analysis.md), from [`scripts/analyse.py`](scripts/analyse.py), fixed before the runs. Checks I made after the runs are labelled as such, and their numbers are in [results/extra-checks.md](results/extra-checks.md). Every figure below comes from those files.

## 1. What I wanted to find out

When a small model running on this machine has to change a storefront to match a backend it can't see in its own repository, does a generated guide to that backend help it? And does the guide help it more than the backend's source code would?

## 2. Why I thought it was worth testing

In [OKF test G](https://github.com/meabs/OKFExperiment/blob/5a090274481d1386ed96e75fa2a90d47c2d4a7c4/results/G-harder-crossrepo-change-tasks.md), the hosted model (`gpt-5.6-luna`) passed:

- 3 of 20 changes with no guide;
- 18 of 20 with the backend's guide;
- 18 of 20 with the backend's source.

So for that model, the guide was a good substitute for the code, but no better than it. A small local model has a quarter of the context (65,536 tokens against 272,000) and works far more slowly, so reading a 1,173-file Java backend should cost it much more than reading a short guide. If reading code is its bottleneck, the guide should beat the source for the local model.

## 3. What I predicted

Three hypotheses, fixed before the runs, one-sided and Holm-adjusted together:

| # | Hypothesis |
| --- | --- |
| H1 | With the guide (`okf`), the local model passes more changes than with no guide (`no_okf`) |
| H2 | With the guide, it passes more changes than with the backend's source (`source`): for a small model, the guide is worth more than the code |
| H3 | Runs with the guide take less time than runs with the source |

## 4. How I tested it

- **Agent:** Codex CLI 0.157 running `qwen3.8:27b` locally (Ollama on the machine's AMD graphics, 4-bit, 65,536-token context), at medium reasoning effort, as in test G. Web search is off in every arm (see "What changed from the design").
- **Isolation:** each run is in a bubblewrap sandbox that shows the agent only its own copy of the storefront. The `source` arm also sees the backend, read-only.
- **Tasks:** test G's four, with the prompts unchanged. Each needs facts that only the backend states:
  1. fix a cart delete that sends the wrong identifier;
  2. add a discount code under the backend's field name;
  3. build a checkout request with six renamed fields;
  4. read an order list whose paging fields come from a parent class.

  The backend's field names were renamed beforehand, so they can't be answered from memory of the public project. Each task has a hidden test that no agent sees. All four fail on the untouched storefront and pass on OKF's reference solution.
- **Arms:**
  - **`no_okf`:** the storefront only, told the backend isn't available;
  - **`okf`:** the storefront with its own guide and the backend's guide, generated by `kgen` at the commit OKF names;
  - **`source`:** the storefront and the backend's source, read-only.
- **Size:** 5 runs per task per arm, 60 runs, one repetition at a time with the arms in rotating order. Time limit: 20 minutes a run.
- **Measure:** a pass is a run that finished and whose hidden test passed. Arms are compared by the mean over the four tasks of each task's pass rate. Permutation tests within tasks (100,000 shuffles), bootstrap intervals within tasks (10,000 resamples), seed 1, Holm over the three.

## 5. What happened

**With the backend's guide, the local model passed every change: 20 of 20, against 4 of 20 with no guide. With the backend's source it passed 19 of 20. The guide was no better than the source, just as for the hosted model.**

**How to read the numbers in this report:**
- A score such as 20/20 is how many runs passed their hidden test out of how many were run. Higher is better: a pass means the change does what the task asked against the backend's real field names.
- For time, tokens, energy and cost, lower is better.

By every cost measure the source runs were slightly cheaper than the guide runs, and both were well ahead of no guide. The no-guide runs worked longest because they searched the storefront for clues that weren't there.

**The arms happened as designed:**
- All 20 guide runs opened the guide.
- All 20 source runs read the backend.
- No run reached anything its arm didn't allow.

**The local model was slower than the hosted one, but not drastically.** The median run took 4.0 to 7.4 minutes, against 38 to 45 seconds for the hosted model in test G: about 6 to 10 times slower. In [test-skill-local](../2026-10-test-skill-local/), on Java tasks, it was 30 to 60 times slower.

**How the failures happened** (from the event streams, checked after the runs):
- **Guessed field names.** 15 no-guide runs finished and failed. In 14 of them, the agent used field names from the storefront's own code, or the public project's original names, instead of the backend's renamed ones. The 15th (task 1) wrongly concluded that the backend has no delete endpoint. Examples: `promoCode` or `discountCode` for the discount code, and `shippingQuote` for the shipping option.
- **Few warnings.** Only 6 of those 15 runs said the backend wasn't available, so their names were unconfirmed. The other 9 presented the guesses as the backend's fields. For example, one said `discountCode` was "the field the Shopizer cart-item model defines".
- **Task 1 without the backend.** The no-guide runs passed task 1 four times from memory of the public project: its delete endpoint and the SKU match aren't renamed. The hosted model passed it three times in test G.
- **The source arm's one failure** (task 3, run 5) reported the six right field names. The grading log doesn't show which check failed, and the run's workspace isn't kept.

## 6. What surprised me

- **The small model read the Java backend well.** I expected a 1,173-file backend to swamp a 65,536-token context. Instead, the source runs found the right classes, including fields in parent classes and the right one of two classes called `PersistableOrder`, at least as cheaply as the guide runs. The model searched with `rg` and read only the few files it needed, so the size of the backend mattered less than I thought.
- **The local model passed more than the hosted one** in both the guide and source arms (20 and 19 against 18 and 18). That is within the noise for five runs a task, and the setups differ, so it shows only that the local model isn't worse at these tasks.
- **The discarded first attempt looked different.** Before the restart (see "What changed from the design"), two guide runs hit the 20-minute limit while still reading the guide. In the 20 measured guide runs, none did, and the slowest took 17.7 minutes. Neither run is analysed, but it is a reminder that a slow model's time limit can decide a result.

## 7. What this might mean in practice

This section is interpretation, not measurement.

- **If a local agent works across repositories, give it the other side.** Without the backend, the local model got 4 changes in 20 right. With either the backend's guide or its code, it got 19 or 20. That gap is far bigger than any difference between models here.
- **A generated guide is a good stand-in when the code can't be shared.** Where the other team's code isn't available (another company's service, a restricted repository), a guide generated from it worked as well as the code itself, for a small model as for a large one.
- **When the code can be shared, the guide adds nothing.** The source runs were as accurate and slightly cheaper. On this evidence, don't build and maintain guides just to help a small model read code it can already read.
- **Risk: without the backend, the agent's report can't be trusted.** In 9 of 15 failed no-guide runs, the agent reported field names it had guessed as if it had checked them. If the change had gone in, the backend would have ignored or rejected those fields, and the agent's report would have said nothing was wrong. A test against the real backend, or the backend's contract, is the only reliable check.
- **Risk: guides go out of date.** The guide here was generated from the exact backend the tests use. A guide behind the code would give wrong names with the same confidence, and this experiment says nothing about how often that happens.
- **Running locally cost almost nothing:** about a fifth of a penny in electricity per run, against about 1.5 to 2.3 US cents at hosted list prices for the same tokens. The price is time: about 4 minutes a run instead of under 1.

## 8. What the experiment does not prove

- **The scope is narrow:** one local model (`qwen3.8:27b`, 4-bit, one context size), one storefront and one backend, four tasks, five runs each.
- **The power is low.** Four tasks can show only large differences. A gap of a run or two between the guide and the source reads as "no measurable difference", so a small advantage either way can't be ruled out.
- **The comparison with the hosted model is informal:** different dates, operating systems, isolation methods and rig versions. The hosted runs had web search and these didn't, so that comparison has no test.
- **The backend's names were renamed by script,** so memory couldn't help. On a real, well-known backend, memory might rescue the no-guide arm more often.
- **The guide was regenerated** with the generator commit OKF names. It may differ in small ways from the copy test G used.
- **The failure explanations were checked after the runs** (guessed names, warnings), from the agents' final messages and event streams, and weren't part of the design.

## 9. What I'd test next

- **A stale guide, on the local model:** OKF test D2 tested stale knowledge with the hosted model; rerunning it locally would show whether a small model checks the source ("read the source to confirm") or trusts an out-of-date guide.
- **A contract instead of a guide, on the local model:** OKF test H1 found an API contract nearly as good as the guide for the hosted model (13 against 14 of 16). A contract is cheaper to keep up to date, so it is worth checking on the small model too.
- **A smaller context or a smaller model,** to find where reading the source stops being affordable and the guide starts to pay.
- **Requiring a warning:** tell the no-guide agent to say which names it could not confirm, and count how often it does.

## Checks on the runs

- **Complete:** all 60 runs were graded. 59 finished, and 1 hit the time limit (no guide, task 3, run 3), counted as a failure. None crashed, and none attempted a web search.
- **Grading:** for every run, the rig's pass or fail matches its grading log (the hidden test's output: `ok`, or "hidden test failed").
- **Model and effort:** all 60 Codex session files name `qwen3.8:27b` at medium effort.
- **Hidden tests not visible:** the sandbox shows only the run's own storefront, plus the backend for `source`. No event stream mentions the experiments folder, where the hidden tests are. No guide or no-guide run mentions the backend's folder.
- **Behaviour claims** (the guide or backend opened, guessed names, warnings) come from the event streams, not from the agents' summaries.

Through Ollama, search needs an Ollama account, so both runs crashed, which would have counted against the no-guide arm. The user chose to restart from the beginning with search off in every arm: "1". The 10 runs finished before the stop were set aside and aren't analysed. They are kept locally, not published, because they include the Codex homes.
